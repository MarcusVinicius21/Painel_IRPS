# M02_03 — Retentativas limitadas e falhas auditáveis
Status: PASS

## Problema corrigido
A seleção anterior permitia repetir indefinidamente tarefas failed. Agora cada operação tem teto de três tentativas. Falhas transitórias ficam failed_retryable; HTTP de acesso/recurso inválido fica blocked; esquema/formato/paginação não verificável fica quarantined. Falha não gera página comprovada, zero compras ou conclusão de escopo. Leases expiradas também respeitam o teto.

Backoff exponencial mínimo de 60/120 segundos antes da segunda/terceira tentativa, com jitter adicional. Retry-After é limite inferior: uma pausa de duas horas não é reduzida para uma hora. Circuito PNCP compartilhado entre publicações, itens e resultados; o executor local mantém throttle de um segundo entre avanços. Não há retentativa em laço dentro da mesma requisição. Outros hosts e coletas independentes continuam disponíveis.

HTTP, URL, hash da resposta, tentativa, categoria e data ficam no audit_event. GET de coleta adiciona recent_errors sem quebrar o contrato anterior. Resposta malformada ou de schema incompatível conserva hash, não conteúdo sensível no relatório. Backoff não é zerado por outro trabalhador. Pausa manual durante uma falha não é sobrescrita. Cobertura reconhece todos os estados de falha novos, sem convertê-los em cobertura positiva.

## Alternativas e limites
O teste de alternativa pública comprova que consultar identidade IBGE não encerra coleta PNCP falha. Não existe fallback silencioso que atribua dados de uma fonte à outra. Fatiamento de janela segue até sete dias e paginação documentada; descoberta TCE continua parcial conforme M01_03. Não se inventou CSV ou endpoint para contornar o ConnectError. Bloqueios permanentes exigem revisão do recurso/esquema; retomar a coleção não ultrapassa o orçamento da tarefa bloqueada.
